### 一. 招投标问答机器人结构

`bidding_agent_03` 是一个面向中文招投标业务的可追溯问答系统。它同时提供：

- Vue 网页端：适合登录、连续问答、上传私有文件、查看历史会话和引用。
- CLI 命令行：适合固定数据集上的批量评估、LLM 选型、Embedding 选型和向量库对比。

网页后端和 CLI 不各自维护一套检索逻辑，而是共同调用 `backend/services/qa_pipeline.py`、`backend/services/rag_service.py` 和同一套生成消息构造逻辑。在相同配置、相同数据库快照、相同问题、无上传文件且关闭历史上下文时，两者的检索证据和生成输入保持一致。

#### 1.1 纵向总体架构图

下面首先完整保留 `bidding_agent_02` 第一章中的原始检索与生成结构；`bidding_agent_03` 不删除或改换这条主链，而是在它的入口、检索证据源、运行服务和输出持久化位置增加新结构。

03 版本的变化是“在原核心 RAG 结构外增加应用与可靠性能力”，不是删除原检索结构：

- 入口增加 Vue/FastAPI 网页端，同时保留 `main.py` CLI。
- Web 与 CLI 通过 `qa_pipeline.py` 和 `rag_service.py` 复用同一检索、上下文和生成逻辑。
- 原五类公共 Milvus 与 `news` 联网结构保持不变，新增按用户隔离的私有文件证据支路。
- 在原检索旁增加完整公告标题标量精确查询，并在原 RRF 和 reranker 节点增加精确命中保护。
- 回答后新增 MySQL 永久持久化以及 Redis/Memurai 的流式事件、取消、限流和文件队列。

#### 1.2 设计边界

- MySQL 保存用户、会话、问答历史、引用、文件和任务状态，不参与招投标业务记录的语义召回。
- Redis/Memurai 保存短期状态、WebSocket 事件、取消标志、限流和文件队列，不是永久问答历史库。
- Milvus Lite 保存公共业务向量和私有文件向量，是本地检索知识库。
- `news` 默认只走 Tavily 联网，不建立本地 `news` 向量库。
- CSV 是公共业务数据的源文件；修改 CSV 后不会自动同步 Milvus，必须重新构建相应类别。
- Windows 本地开发使用 Milvus Lite 时，只允许一个进程持有同一个数据库目录锁。

### 二. 整体技术栈总结

#### 2.1 应用层

| 层级 | 技术 | 当前用途 |
|---|---|---|
| 网页前端 | Vue 3、TypeScript、Vite | 登录、会话、问答、流式显示、引用展示、文件上传 |
| Web API | FastAPI、Uvicorn | REST、WebSocket、鉴权、健康检查、业务编排 |

#### 2.2 数据与状态层

| 组件 | 技术 | 当前用途 |
|---|---|---|
| 关系数据库 | MySQL 8 + SQLAlchemy Async + asyncmy | 用户、会话、消息、引用、文件、生成任务 |
| 数据库迁移 | Alembic | 建表与版本迁移 |
| 缓存/队列 | Redis 或 Windows Memurai | 上下文缓存、事件流、任务取消、限流、文件队列 |
| 公共向量库 | Milvus Lite | enterprise、tender、product、laws、policy |
| 私有向量库 | Milvus Lite | 用户上传文件的切片、Dense 与 BM25 索引 |
| 源数据 | CSV、法律与政策文本 | 公共向量库构建输入 |

#### 2.3 检索与生成层

| 能力 | 技术或实现 |
|---|---|
| 中文 Embedding | `BAAI/bge-base-zh-v1.5`，本地离线加载 |
| 稠密检索 | Milvus COSINE 向量相似度 |
| 稀疏检索 | Milvus BM25 + jieba 中文分词 |
| 检索规划 | DeepSeek Function Calling + Pydantic 校验 + 确定性回退 |
| 精确标题 | Milvus `title` 标量等值查询，优先于语义召回结果 |

| 重排 | LLM reranker，精确标题命中记录受保护 |

| 答案生成 | DeepSeek Chat Completions 流式输出 |
| 引用 | 统一构造 `[E1]`、`[E2]` 等证据编号 |

#### 2.4 文件与安全层

| 能力 | 当前实现 |
|---|---|
| 用户认证 | JWT access/refresh token、Argon2 密码哈希 |
| 文件类型 | PDF、TXT、MD、DOCX |
| 文件校验 | 扩展名、MIME、文件头、大小、SHA-256 去重 |
| 异步解析 | 独立 `file_worker` 消费 Redis Stream |
| 用户隔离 | 私有文档按 `owner_user_id`、`file_id` 过滤 |
| 可靠流式 | Redis Stream 保存事件序号，支持断线恢复 |
| 输出安全 | Markdown 解析后使用 DOMPurify 清理 HTML |

#### 2.5 本版本明确不做的事情

- 不直接对 MySQL 中的招投标业务表生成 SQL 查询。
- 不把 Redis 当作永久历史数据库。
- 不让 Web 和 CLI 分别实现两套检索算法。
- 不在 Milvus Lite 模式下启动多个 API worker 争用同一数据库文件。
- 不保证温度为 0 的两次云模型请求逐字节完全相同；它保证的是采样更稳定，而不是供应商侧的绝对确定性。

### 三. 当前完整技术架构说明

#### 3.1 Web 与 CLI 双入口

Web 入口是 `backend/main.py` 中的 FastAPI 应用，CLI 入口是根目录 `main.py`。两者共同使用：

- `backend/services/qa_pipeline.py`：统一检索上下文和生成消息。
- `backend/services/rag_service.py`：统一异步 RAG 检索编排。
- `backend/services/tavily_client.py`：统一异步联网检索。
- `backend/services/deepseek_stream.py`：统一流式答案请求。
- `generation/answer_generator.py`：统一系统提示词和消息模板。

Web 额外负责登录、会话、上传文件、历史记录、任务取消和 WebSocket；CLI 则直接读取问题并输出结果。CLI 不需要 MySQL 用户和会话，但公共检索和生成逻辑与 Web 共用。

要比较两端结果，必须同时满足：

1. 使用同一个 `.env`。
2. 使用同一份 CSV 和 Milvus 数据库快照。
3. 问题文本完全相同。
4. 网页端没有选择上传文件作为证据范围。
5. `CONTEXT_TURNS=0`，或两端显式提供完全相同的历史消息。
6. 修改配置后已重启后端；CLI 也以新进程重新运行。

#### 3.2 FastAPI 生命周期与健康检查

`backend/app.py` 创建应用并挂载 API 路由。启动时初始化配置、MySQL、Redis 及共享服务；关闭时释放连接。

- `/api/v1/health/live`：只证明 Web 进程仍在运行。
- `/api/v1/health/ready`：检查 MySQL 和 Redis 是否可用；任一失败返回 `503 not_ready`。
- `live=200` 但 `ready=503` 表示程序活着，但依赖尚未满足，不能视为完整可用。

#### 3.3 用户认证与权限

`backend/api/auth.py` 提供登录、刷新、退出和当前用户接口。密码由 Argon2 哈希保存，JWT 分为短期 access token 和长期 refresh token。

WebSocket 握手也必须携带有效身份。后端出现 `WebSocket ... 403` 通常表示 token 缺失、失效或前端还保存着旧登录状态，而不是 Milvus 检索错误。

#### 3.4 MySQL 持久化模型

MySQL 通过 SQLAlchemy 异步会话访问，Alembic 管理结构版本。核心表包括：

- `users`：用户名、密码哈希、启用状态、创建时间。
- `conversations`：用户会话标题及归属。
- `messages`：用户问题和助手答案。
- `message_citations`：某条助手消息对应的证据引用。
- `uploaded_files`：原文件名、存储名、哈希、解析状态和错误。
- `generation_jobs`：一次回答任务的运行、完成、取消或失败状态。
- `alembic_version`：数据库迁移版本。

Repository 层集中处理查询和权限边界，Service 层组合业务流程，API 层只负责协议、参数和返回值。

#### 3.5 Redis/Memurai 的职责

Redis 在 Windows 本地可由 Memurai Developer 替代，接口和协议保持 Redis 兼容。当前用途包括：

- 缓存最近若干轮对话上下文。
- 保存流式回答事件及递增序号，支持客户端重连后续传。
- 保存生成任务的取消标志。
- 限制单用户并发生成数和请求频率。
- 使用 Redis Stream 投递文件解析任务。
- 由 worker 使用 consumer group 消费、确认和回收超时 pending 任务。

即使 `CONTEXT_TURNS=0`，Redis 仍可能被 WebSocket、限流、取消和文件队列使用，因此网页端完整就绪检查仍要求 Redis 正常。

#### 3.6 WebSocket 流式回答协议

客户端可发送：

- `ask`：提交问题和可选文件范围。
- `stop`：取消当前回答。
- `resume`：从指定事件序号继续接收。
- `ping`：连接保活。

服务端可发送：

- `ack`：任务已接收。
- `status`：规划、检索、重排或生成阶段状态。
- `token`：增量答案文本。
- `citations`：结构化证据列表。
- `done`：回答完成。
- `cancelled`：任务已取消。
- `error`：错误码和可读提示。
- `pong`：保活响应。

`backend/services/generation_manager.py` 控制同一用户的活动任务，`chat_service.py` 负责整条问答业务，`deepseek_stream.py` 负责读取上游 SSE 流。

#### 3.7 检索规划

`planning/retrieval_planner.py` 让 DeepSeek 通过 Function Calling 输出结构化计划，主要字段包括目标类别、子类别、检索词、元数据过滤和是否联网。

规划结果必须经过 Pydantic 校验。遇到超时、无效 JSON、未知类别或字段异常时，使用确定性回退计划，避免模型规划器成为单点故障。

规划器只决定“还要检索什么”，不能否决完整公告标题的精确命中。

#### 3.8 完整公告标题精确匹配优先

这是 `bidding_agent_03` 的关键可靠性机制：

1. 从用户问题中提取可能的完整公告标题。
2. 在目标 Milvus collection 中对 `title` 做标量等值查询。
3. 精确命中记录标记 `exact_title_match=true`。
4. 即使 LLM 规划器选错关键词或类别，精确查询仍独立执行。
5. RRF 融合时精确命中固定优先。
6. LLM 重排器不得把精确命中淘汰或降到普通相似记录之后。
7. 最终上下文中精确记录排在证据前部。

该机制解决“CSV 和 Milvus 明明存在完整标题，却因向量相似度或重排只返回同类公告”的问题。它要求 Milvus 中已经存在该记录，而且 `title` 字段与规范化后的查询标题一致。

#### 3.9 六类路由与数据来源

系统对外保留六个业务类别：

| 类别 | 默认来源 | 主要内容 |
|---|---|---|
| `enterprise` | 本地 Milvus | 企业资质、能力、主体资料 |
| `tender` | 本地 Milvus | 招标、采购、成交、结果公告 |
| `product` | 本地 Milvus | 产品参数、价格、型号与供应信息 |
| `laws` | 本地 Milvus | 法律法规 |
| `policy` | 本地 Milvus | 政策、规范性文件 |
| `news` | Tavily 联网 | 最新动态和时效性新闻 |

用户上传文件不是第七个公共类别，而是一个按用户隔离的私有证据源，可与上述公共证据一同进入融合与答案上下文。

#### 3.10 Milvus 数据布局

公共类别分别使用独立目录和数据库文件：

```text
milvus_db/
├─ enterprise/main.db
├─ tender/main.db
├─ product/main.db
├─ laws/main.db
├─ policy/main.db
└─ private/main.db
```

每个公共类别由配置定义 collection、主键、文本字段、标题字段、向量字段、BM25 字段和允许过滤字段。不同类别可以有自己的子类别 collection。

Milvus Lite 对数据库目录加进程锁。出现 `DataDirLockedError` 表示另一个后端、CLI、测试或构建进程仍持有同一 `main.db`，应先关闭重复进程，再启动唯一实例，不能删除锁文件或数据库来规避。

#### 3.11 元数据过滤安全

`retrieval/metadata_filter.py` 不直接拼接模型生成的任意表达式，而是根据每个类别的允许字段表编译过滤条件。

- 未知字段被拒绝或忽略。
- 空过滤统一规范化。
- 字符串正确转义。
- 私有文档强制加入用户和文件范围条件。

这既降低 Milvus 表达式错误，也防止跨用户读取私有文件。

#### 3.12 Dense 与 BM25 混合检索

Dense 检索使用 `BAAI/bge-base-zh-v1.5` 将问题编码为向量，擅长语义近似。BM25 使用稀疏词项权重，擅长标题、单位名、型号和专有名词。

两路排名必须保留为独立列表，再用 RRF 融合。不能先把 Dense 和 BM25 分数直接相加，因为两种分数的量纲不同。

当前各类别最低相似度基准为：

| 类别 | 阈值 |
|---|---:|
| enterprise | 0.68 |
| tender | 0.65 |
| product | 0.66 |
| laws | 0.62 |
| policy | 0.62 |

阈值用于减少弱相关结果，但精确标题命中不应被普通向量阈值淘汰。

#### 3.13 RRF 融合、去重与精确命中保护

`ranking/result_fusion.py` 根据名次而不是原始分数计算 Reciprocal Rank Fusion。它还负责：

- 融合 Dense 与 BM25 结果。
- 跨 collection 去重。
- 保留来源、类别和元数据。
- 将精确标题命中置顶并防止截断。

#### 3.14 LLM 重排

`ranking/reranker.py` 将候选证据交给 LLM 判断与问题的业务相关性。无论重排返回什么顺序，`exact_title_match=true` 的证据都会被重新保护到前部。

如果重排失败、超时或格式错误，系统退回融合排名，不会让整个检索失败。

#### 3.15 Tavily 联网检索

联网检索主要在以下情况触发：

- 问题明确要求“最新”“今天”“新闻”或外部网页。
- 计划类别为 `news`。
- 本地证据不足或重排后有效结果过少。
- 用户明确要求核验联网来源。

域名过滤在请求前和返回后都执行，避免服务端忽略过滤条件时引入不需要的网站。联网失败只代表本次没有获得网页证据，不能据此断言网页或事实不存在。

#### 3.16 上下文构造与答案生成

`generation/context_builder.py` 把公共、私有和联网证据统一编号为 `[E1]`、`[E2]` 等，限制总长度并保留来源元数据。

`generation/answer_generator.py` 定义系统提示词，要求模型：

- 只根据证据回答可核验业务事实。
- 对关键结论标注证据编号。
- 证据不足时明确说明不足。
- 不把相似项目当成用户询问的同一项目。

`qa_pipeline.py` 统一把问题、可选历史、检索上下文和生成配置组成消息。Web 与 CLI 都使用 `settings.answer_temperature`。

#### 3.17 私有文件上传与异步处理

上传流程如下：

1. API 校验登录用户、扩展名、MIME、文件头和大小。
2. 计算 SHA-256，避免同一用户重复上传相同文件。
3. 使用随机存储名写入受控目录，阻止路径穿越。
4. MySQL 创建 `uploaded_files` 记录。
5. Redis Stream 投递解析任务。
6. `backend.workers.file_worker` 提取 PDF/TXT/MD/DOCX 文本。
7. 按约 1200 字符、120 字符重叠切片。
8. 写入私有 Milvus collection，并保存 `owner_user_id`、`file_id` 等元数据。
9. 更新文件状态为完成或失败。

worker 命令启动后“没有输出”通常表示它正在阻塞等待 Redis 队列，这是正常的常驻服务行为。上传文件后才会出现处理日志。

#### 3.18 评估架构边界

模型评估时必须区分三个变量层：

- LLM 选型：固定问题集、检索计划、候选证据、上下文和引用，只替换答案模型。
- Embedding 选型：固定答案模型和测试集，分别重建向量库，比较 Recall@K、MRR、精确标题召回和引用正确率。
- 向量库选型：固定 Embedding、切片、字段、距离度量、TopK 和答案模型，只替换存储/检索引擎。

否则一次同时改多个变量，无法知道精度变化来自模型、向量、数据库还是提示词。

### 五. 数据库与知识库分工

#### 5.1 MySQL：业务状态的永久存储

MySQL 负责“谁问了什么、系统回答了什么、任务和文件处于什么状态”，适合事务、关联和历史查询。

| 数据 | 保存位置 | 是否参与公共语义召回 |
|---|---|---|
| 用户与密码哈希 | `users` | 否 |
| 会话 | `conversations` | 否 |
| 用户问题和答案 | `messages` | 默认否 |
| 答案引用 | `message_citations` | 否 |
| 文件元数据和状态 | `uploaded_files` | 只用于定位私有向量 |
| 回答任务状态 | `generation_jobs` | 否 |

问答历史存入 MySQL 不等于自动成为知识库。若未来要把优质历史回答用于检索，必须单独设计审核、脱敏、切片和向量化流程。

#### 5.2 Redis/Memurai：短期状态和可靠事件

| 数据 | 作用 | 生命周期 |
|---|---|---|
| 最近对话上下文 | 多轮问答提示 | TTL 到期或主动清理 |
| WebSocket 事件流 | 重连续传 | 按长度/TTL 裁剪 |
| 取消标志 | 中止生成 | 任务结束后清理 |
| 并发和频率计数 | 防止滥用 | 短 TTL |
| 文件任务 Stream | 异步解析队列 | 消费确认后保留/裁剪 |

Redis 故障不会删除 MySQL 已持久化历史，但会影响 ready 状态、流式恢复、取消、限流和文件 worker。

#### 5.3 公共 Milvus：五类本地业务知识

| 类别 | 典型源数据 | 适合回答 |
|---|---|---|
| enterprise | 企业 CSV/结构化资料 | 企业资质、主体和能力 |
| tender | `tender.csv` 等公告数据 | 招标项目、采购单位、成交供应商、金额、日期 |
| product | `product.csv` | 产品规格、品牌、型号、价格 |
| laws | 法律文本 | 法律条款和法定要求 |
| policy | 政策文本 | 地方政策、通知和办事规则 |

Milvus 是由源数据构建出的检索快照。CSV 修改后：

1. 先备份目标 `milvus_db/<category>`。
2. 停止所有占用该数据库的进程。
3. 对正确类别执行构建器 `--rebuild`。
4. 检查实体数、随机样本、关键 ID 和精确标题查询。
5. 通过后再用于评估或生产。

#### 5.4 私有 Milvus：上传文件知识库

私有 collection 保存文件切片而不是原文件本身。每条向量至少携带：

- `owner_user_id`：用户隔离。
- `file_id`：选择某些文件作为本次证据。
- `chunk_index`：切片顺序。
- `title` 或原文件名。
- 原始文本与向量字段。

所有私有检索必须强制加入当前用户过滤条件，不能只依赖前端传来的 `file_id`。

#### 5.5 Tavily：时效性外部证据

Tavily 适合最新新闻、网页核验和本地库缺失内容。它不替代本地数据库：

- 网络超时或反爬只表示没有取得证据。
- 外部网页内容可能变化，评估时应记录抓取时间和 URL。
- 做可重复模型评估时，建议冻结联网结果或关闭联网，否则不同时间的证据会漂移。

#### 5.6 数据真实性优先级

推荐按以下顺序判断事实：

1. 完整标题精确命中的本地原始公告记录。
2. 用户明确选择的私有原始文件。
3. 本地语义检索到的相关业务记录。
4. 权威官网的联网证据。
5. 其他网页证据。
6. LLM 自身知识只能解释，不可替代项目事实证据。

#### 6.3 三个关键参数什么时候设置为多少

推荐先按使用场景选择整组配置，而不是单独随意修改一个值：

| 使用场景 | `CONTEXT_TURNS` | `ANSWER_TEMPERATURE` | `MILVUS_THREAD_LIMIT` | 说明 |
|---|---:|---:|---:|---|
| CLI 单轮基准评估 | `0` | `0` | `1` | 最适合当前 LLM/Embedding/向量库选型 |
| Web 与 CLI 对齐验证 | `0` | `0` | `1` | 排除历史和采样差异，Windows Lite 最稳 |
| 生产型单轮证据问答 | `0` | `0` | `1` | 每个问题独立，回答偏严谨 |
| Web 多轮追问 | `3`～`5` | `0` | `1` | 支持“它的金额呢”之类省略式追问 |
| 内部演示、语言更自然 | `3`～`5` | `0.1`～`0.3` | `1` | 措辞更灵活，但不适合作严格文本对比 |
| 独立 Milvus Server 压测后 | 按业务 | 按业务 | `2`～`4` 起测 | 仅迁移出 Lite 且压测证明安全后增加 |

##### `CONTEXT_TURNS`

含义：生成当前回答时，最多加入多少轮最近会话。这里一轮通常指一组用户问题和助手回答。

- 设为 `0`：完全单轮。适合数据集评估、CLI 批处理、Web/CLI 对齐和独立问题。
- 设为 `1`～`2`：只需要短追问，token 成本较低。
- 设为 `3`～`5`：常规网页多轮问答推荐范围。
- 设为 `6`～`10`：长对话场景才考虑，需要关注上下文污染、成本和延迟。
- 不建议盲目设很大：旧问题可能误导检索或答案，并使不同样本不再独立。

当值大于 `0` 时，网页会从缓存/历史中加入前文，而当前 CLI 默认没有等价的会话历史输入。因此做两端一致性测试时应保持 `0`。

##### `ANSWER_TEMPERATURE`

含义：答案生成阶段的随机性，不改变 Milvus 的召回算法。

- 设为 `0`：严谨问答、模型评估、事实抽取和回归测试的默认值。
- 设为 `0.1`～`0.2`：略微改善表达自然度，事实任务仍较克制。
- 设为 `0.3`：适合内部演示、改写或摘要，不建议用于精确答案基准。
- 不建议招投标事实问答高于 `0.3`，温度越高，措辞和结构波动越大，也更难复现实验。

即使设置为 `0`，云端模型服务的实现、模型版本或并发调度仍可能让两次答案有细微差异。需要逐字节一致时应固定并缓存同一次模型输出；模型选型评估则应比较事实正确性、引用和结构指标，而不是只比较字符串。

##### `MILVUS_THREAD_LIMIT`

含义：当前进程允许并行执行 Milvus 阻塞操作的线程上限，不是 Milvus collection 数量，也不是 API worker 数。

- Windows + Milvus Lite：固定为 `1`。这是当前项目最安全的默认值。
- 独立 Milvus Server：先从 `2` 开始，在固定并发下观察 P95 延迟、错误率、CPU 和连接数，再考虑 `4`。
- 不要仅因机器 CPU 核心多就提高。Milvus Lite 的文件锁和本地 SQLite 风格资源约束不会因此消失。
- 如果出现 `DataDirLockedError`，降低线程数通常不是根治方式；要检查是否启动了多个进程占用同一数据库。

#### 6.4 与上述参数配套的 `API_WORKERS`

| 模式 | 推荐值 | 原因 |
|---|---:|---|
| Windows 本地 Milvus Lite | `1` | 避免多个进程打开同一 `main.db` |
| 单机 CLI | 不适用 | CLI 本身就是单进程入口 |
| 独立 Milvus Server + 共享 MySQL/Redis | `2` 起压测 | 各 worker 不再争用 Lite 文件，但仍需评估资源 |

在 `MILVUS_MODE=lite` 时，不应把 `API_WORKERS` 调到 `2` 或更高。

#### 6.5 检索与模型配置

| 配置 | 推荐默认 | 什么时候调整 |
|---|---|---|
| `EMBEDDING_MODEL` | `BAAI/bge-base-zh-v1.5` | 进行 Embedding 对比实验时修改，并重建全部受影响向量库 |
| `ANSWER_MODEL` | 当前 DeepSeek 回答模型 | LLM 选型时只改此项，固定证据上下文 |
| `PLANNER_MODEL` | 当前 DeepSeek 规划模型 | 评估规划准确率、成本或延迟时修改 |
| `RERANK_MODEL` | 当前 DeepSeek 重排模型 | 评估候选排序时修改，需冻结召回候选 |
| `TOP_K` 类参数 | 保持基准配置 | 召回率不足时逐步增加，同时观察噪声和 token |
| 类别阈值 | 当前 0.62～0.68 | 基于标注集画出召回/精度曲线后调整 |

#### 6.6 MySQL、Redis 和鉴权配置

| 配置组 | 建议 |
|---|---|
| `MYSQL_*` / `DATABASE_URL` | 指向专用数据库，不使用空数据库名；生产避免 root |
| `REDIS_URL` | 本地使用 `redis://127.0.0.1:6379/...`；生产使用受控实例 |
| JWT secret | 使用足够长的随机值，开发和生产分开 |
| access token 时长 | 较短，降低泄露风险 |
| refresh token 时长 | 较长，但需要轮换和退出失效机制 |
| 限流/并发 | 根据单用户公平性和上游 API 限额压测后调整 |

#### 6.7 文件配置

| 配置 | 调整原则 |
|---|---|
| 最大文件大小 | 先按业务文档常见大小，增大时同步评估磁盘、解析内存和超时 |
| 允许扩展名 | 只开放已实现安全解析的 PDF/TXT/MD/DOCX |
| chunk size | 当前约 1200 字符；长条款可增大，细粒度定位可减小 |
| chunk overlap | 当前约 120 字符；避免跨边界语义丢失，但过大会造成重复召回 |
| worker 数量 | Lite 数据库仍应谨慎保持单写者；独立 Milvus 后再压测扩展 |

#### 6.8 修改配置后的生效规则

- `.env` 在进程启动时读取。
- 修改后端配置后，必须停止并重新启动 Uvicorn。
- worker 有独立进程，涉及 Redis、文件或 Milvus 配置时也要重启 worker。
- CLI 每次启动新进程都会重新读取配置。
- 前端 Vite 只读取自己的构建/代理配置；后端 `.env` 改动不要求重启 Vite，但后端必须重启。
- 评估报告必须记录 `.env` 中非密钥配置、代码版本、数据快照、向量构建参数和模型名称。

#### 6.9 `.env` 全量配置、默认值和调整影响

##### 6.9.2 Embedding、向量库和检索

| 配置 | 默认值 | 含义 | 参数变化的影响 |
|---|---|---|---|
| `VECTOR_DB_ROOT` | `milvus_db` | 五类公共向量库根目录 | 修改后程序会读取另一套数据库目录；目录不存在时检索为空，更换目录不等于迁移数据 |
| `EMBEDDING_MODEL` | `BAAI/bge-base-zh-v1.5` | 文档和查询使用的向量模型 | 修改后必须用同一模型重建相关向量库；新旧向量空间不可混用 |

| `ENTERPRISE_THRESHOLD` | `0.68` | 企业向量 Dense 最低相似度 | 提高会减少噪声但增加漏召回；降低会增加召回和 Reranker 压力 |
| `TENDER_THRESHOLD` | `0.65` | 招投标项目 Dense 最低相似度 | 提高偏精确、降低偏召回；应依据标注问题调整 |

| `LAWS_THRESHOLD` | `0.62` | 法律法规 Dense 最低相似度 | 提高可能漏掉相关条款和释义；降低会增加相似但不适用条款 |
| `POLICY_THRESHOLD` | `0.62` | 政策文件 Dense 最低相似度 | 调整影响政策片段的召回/精度平衡，不能代替有效期和适用范围判断 |

| `SEARCH_ALL_CATEGORIES` | `true`（本机兼容项） | 旧版本的全分类搜索开关 | 当前主检索链路没有直接读取该变量，修改不会改变当前 Planner 的分类路由 |

| `RERANK_MODE` | `llm` | 重排模式；`llm` 调用模型，`off` / `none` / `rrf` 保留 RRF 顺序 | 关闭可减少费用和延迟，但跨类别候选只依赖 RRF，相关性排序可能下降 |

| `FINAL_CANDIDATE_LIMIT` | `20` | Reranker 最终保留候选上限，代码约束 `1`～`50` | 增大为上下文多样性提供更多选择但增加后续处理量；最终仍受上下文限制 |
| `RERANK_WEB_THRESHOLD` | `0.55` | 本地最高重排分低于该值时触发联网补充 | 提高会更频繁联网、增加延迟和费用；降低会更依赖本地证据，可能错过最新信息 |

##### 6.9.3 最终证据上下文

| 配置 | 默认值 | 含义 | 参数变化的影响 |
|---|---|---|---|
| `MAX_CONTEXT_CHARS` | `28000` | 最终证据上下文总字符上限，代码最低按 `4000` 处理 | 增大可容纳更多证据但增加模型 token、费用和延迟；减小可能截掉后续分类或关键例外条款 |

| `ACCESS_TOKEN_MINUTES` | `15` | Access Token 有效分钟数，代码范围 `5`～`120` | 增大减少重新认证但扩大泄露窗口；减小更安全但刷新频率上升 |

| `STREAM_TTL_SECONDS` | `900` | Redis Stream 事件保留秒数，代码范围 `60`～`86400` | 增大可支持更晚重连但增加 Redis 占用；减小可能导致客户端恢复时事件已过期 |
| `STREAM_MAX_EVENTS` | `4000` | 单消息流最大事件数，代码范围 `100`～`20000` | 增大支持更长输出但增加 Redis 存储；减小可能截掉过早的 token 事件，完成结果仍应从消息历史读取 |
| `MILVUS_MODE` | `lite` | 私有上传向量层运行模式，可选 `lite` / `server` | `lite` 适合单机单 worker；切到 `server` 前必须完成 URI、数据迁移、权限和负载验证 |
| `PRIVATE_MILVUS_URI` | `milvus_db/private/main.db` | 私有上传文件向量库地址 | 修改会切换私有向量存储；指向新路径时旧上传向量不会自动迁移 |
| `API_WORKERS` | `1` | Uvicorn API 进程数，代码范围 `1`～`32` | Lite 模式必须为 `1`，否则启动配置校验失败；Server 模式才可从 `2` 开始压测 |
| `MILVUS_THREAD_LIMIT` | `4`（代码和模板回退值） | 每个进程允许同时执行 Milvus 阻塞操作的线程数，代码范围 `1`～`16` | 增大可能提高 Server 模式并发，也会增加连接和锁竞争；Windows Milvus Lite 运行建议仍设为 `1` |
| `UPLOAD_ROOT` | `uploads` | 上传文件落盘根目录 | 修改会切换文件目录；旧文件不会自动移动，目录权限或磁盘不足会导致上传失败 |
| `PRIVATE_COLLECTION` | `private_documents` | 私有文档 Milvus collection 名称 | 修改后会使用另一 collection，原有私有向量不会自动迁移或显示 |
| `FILE_WORKER_STREAM` | `bidding:file-jobs` | Redis 文件解析任务 Stream 名称 | API 与 worker 必须一致；修改一端会导致上传任务无人消费 |
| `FILE_WORKER_GROUP` | `file-workers` | 文件任务 Redis Consumer Group 名称 | 修改会形成新的消费组和 pending 状态；API/worker 部署需要统一并评估旧任务迁移 |

##### 6.9.6 配置调整边界

- 阈值、Top-K、RRF、Reranker 和上下文参数必须基于固定问题集比较 Recall@K、MRR、nDCG、引用正确率、延迟和 token，不能只凭单个示例调整。
- `EMBEDDING_MODEL`、`VECTOR_DB_ROOT`、Milvus URI 或 collection 变化涉及向量兼容性或数据位置，不能只重启进程后继续假定旧数据可用。
- `MAX_CONTEXT_PER_SOURCE` 是来源多样性优先值，不是硬上限；其他来源不足时会回填同一文档的候选。
- `SEARCH_ALL_CATEGORIES`、`NEWS_THRESHOLD` 和独立 `MYSQL_*` 属于兼容/保留配置，当前主链路的实际行为分别由 Planner、news 联网边界和 `DATABASE_URL` 决定。
- 生产环境不得继续使用示例数据库密码、JWT 占位值或开发 Cookie 设置，所有密钥都应通过部署环境安全注入。

#### 8.11 LLM 模型选型推荐流程

1. 设置 `CONTEXT_TURNS=0`、`ANSWER_TEMPERATURE=0`。
2. 冻结标注问题集、公共/私有证据范围和联网结果。
3. 首先运行一次检索并保存候选证据、排序和最终上下文。
4. 对每个候选 LLM 输入同一份消息，只替换 `ANSWER_MODEL`。
5. 统计事实准确率、拒答正确率、引用准确率、格式合规率、延迟和成本。
6. 不要把不同 LLM 自己产生的检索计划差异混入纯答案模型评估；规划模型应单独评估。

#### 8.12 Embedding 与向量库选型推荐流程

1. 固定答案模型、规划器、reranker、问题集、切片和 TopK。
2. 每更换一个 Embedding，使用该模型重建独立向量库快照。
3. 保存模型名、维度、距离度量、collection schema 和构建时间清单。
4. 比较 Recall@K、MRR、精确标题命中率、检索延迟和存储占用。
5. 再把相同 Embedding/数据/schema 分别导入候选向量库，比较引擎差异。
6. 最后才进行端到端答案评估，避免无法定位误差来源。

#### 8.13 Web 与 CLI 一致性检查

使用同一问题验证时：

```ini
CONTEXT_TURNS=0
ANSWER_TEMPERATURE=0
MILVUS_THREAD_LIMIT=1
```

同时保证网页未勾选私有文件、数据库快照相同、后端已重启。比较顺序建议为：

1. 检索计划是否相同。
2. 精确标题命中是否相同。
3. 证据 ID 和顺序是否相同。
4. 生成消息是否相同。
5. 最后比较答案事实和引用；不要只要求字符串逐字相同。
